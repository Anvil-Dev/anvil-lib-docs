# Datagen Integration: Providers & Template Generation (`dev.anvilcraft.lib.v2.registrum.providers`)

<BranchContextCard branch="26.2" />

Another core strength of `module.registrum` is unifying scattered Data Providers under `RegistrumDataProvider`. Beyond chaining `.blockstate(...)`, `.model(...)`, `.loot(...)`, `.recipe(...)`, `.tag(...)`, and `.lang(...)` directly on `BlockBuilder` / `ItemBuilder`, you can also inject global datapack registry entries (worldgen, enchantments, multiblock definitions), global recipes, advancements, and third-party `DataProvider`s anytime via `REGISTRUM.addDataGenerator(ProviderType, callback)` or `REGISTRUM.getDataGenInitializer()`.

---

## 1. Built-in `ProviderType` & `GeneratorType` Overview

Located in `dev.anvilcraft.lib.v2.registrum.providers.ProviderType`.

| Constant (`ProviderType.*`) | Logical Side | Associated Provider / Generator | Description |
| :--- | :---: | :--- | :--- |
| **`DYNAMIC`** | `SERVER` | `RegistrumDatapackProvider` | Extends NeoForge `DatapackBuiltinEntriesProvider`; outputs built-in datapack registry entries added via `DataProviderInitializer#add` and provides updated `HolderLookup.Provider` to dependent providers. |
| **`DATA_MAP`** | `SERVER` | `RegistrumDataMapProvider` | Extends NeoForge `DataMapProvider` to generate fuel, compost, oxidization, and other DataMap JSONs. |
| **`RECIPE_RUNNER`** / **`RECIPE`** | `SERVER` | `RegistrumRecipeRunner` / `RegistrumRecipeProvider` | `RECIPE` is a `GeneratorType<RegistrumRecipeProvider>` under `RECIPE_RUNNER` for generating all recipes. |
| **`ADVANCEMENT`** | `SERVER` | `RegistrumAdvancementProvider` | Generates advancements (`data/<ns>/advancement/*.json`), supporting conditional advancements via `withConditions(AdvancementHolder, List<ICondition>)`. |
| **`LOOT`** | `SERVER` | `RegistrumLootTableProvider` | Generates block loot tables (`LootType.BLOCK` → `RegistrumBlockLootTables`), entity loot tables (`LootType.ENTITY` → `RegistrumEntityLootTables`), and arbitrary `ContextKeySet` loot tables. |
| **`BLOCK_TAGS`** | `SERVER` | `RegistrumTagsProvider.IntrinsicImpl<Block>` | Block tags provider. |
| **`ITEM_TAGS`** | `SERVER` | `RegistrumItemTagsProvider` | Item tags provider (declares a topological dependency on `BLOCK_TAGS` by default, supporting `prov.copy(blockTag, itemTag)` to copy block tags directly to item tags). |
| **`FLUID_TAGS`** | `SERVER` | `RegistrumTagsProvider.IntrinsicImpl<Fluid>` | Fluid tags provider. |
| **`ENTITY_TAGS`** | `SERVER` | `RegistrumTagsProvider.IntrinsicImpl<EntityType<?>>` | Entity type tags provider. |
| **`ENCHANTMENT_TAGS`** | `SERVER` | `RegistrumTagsProvider.Impl<Enchantment>` | Dynamic enchantment registry tags provider. |
| **`DAMAGE_TYPE_TAGS`** | `SERVER` | `RegistrumTagsProvider.Impl<DamageType>` | Dynamic damage type registry tags provider. |
| **`GENERIC_SERVER`** | `SERVER` | `RegistrumGenericProvider` | Mounts any third-party server-side `DataProvider`. |
| **`MODEL`** / **`BLOCKSTATE`** / **`ITEM_MODEL`** | `CLIENT` | `RegistrumModelProvider` / `RegistrumBlockModelGenerator` / `RegistrumItemModelGenerator` | Client model and blockstate providers. |
| **`LANG`** | `CLIENT` | `RegistrumLangProvider` | Language file provider: while generating `en_us.json`, automatically generates `en_ud.json` (Upside-Down English, preserving `%s` / `%1$d` format specifiers unflipped). |
| **`GENERIC_CLIENT`** | `CLIENT` | `RegistrumGenericProvider` | Mounts any third-party client-side `DataProvider`. |

## 2. Full Code Examples

### 1. Registering Datapack Built-in Entries (Multiblocks, Enchantments, Worldgen) & Tag Dependencies

```java
package com.example.mymod.data;

import com.example.mymod.MyMod;
import dev.anvilcraft.lib.v2.multiblock.init.LibRegistries;
import dev.anvilcraft.lib.v2.registrum.providers.DataProviderInitializer;
import dev.anvilcraft.lib.v2.registrum.providers.ProviderType;
import net.minecraft.tags.BlockTags;
import net.minecraft.tags.ItemTags;

public final class ModDataGenSetup {
    public static void configure() {
        DataProviderInitializer init = MyMod.REGISTRUM.getDataGenInitializer();

        // 1. Add Bootstrap to the DYNAMIC datapack provider (e.g., ModMultiblockDefinitions::bootstrap)
        init.add(LibRegistries.DEFINITIONS_KEY, ModMultiblockDefinitions::bootstrap);

        // 2. If a dynamic tag provider references entries generated by DYNAMIC, declare a topological dependency:
        init.addDependency(ProviderType.ENCHANTMENT_TAGS, ProviderType.DYNAMIC);

        // 3. Add global datagen callbacks not tied to a single entry (e.g., copying block tags to item tags)
        MyMod.REGISTRUM.addDataGenerator(ProviderType.ITEM_TAGS, prov -> {
            prov.copy(BlockTags.SLABS, ItemTags.SLABS);
            prov.copy(BlockTags.STAIRS, ItemTags.STAIRS);
        });
    }
}
```

### 2. Generating Full Recipe Families with `RegistrumRecipeProvider` & `DataIngredient`

`RegistrumRecipeProvider` extends vanilla `RecipeProvider` and also implements `RecipeOutput` (so you can pass `prov` directly to `save(prov)`!), while providing template methods built on `DataIngredient` that auto-name recipes and attach unlock criteria (`unlockedBy("has_...", ...)`):

```java
package com.example.mymod.data;

import com.example.mymod.MyMod;
import com.example.mymod.init.ModBlocks;
import com.example.mymod.init.ModItems;
import dev.anvilcraft.lib.v2.registrum.providers.ProviderType;
import dev.anvilcraft.lib.v2.registrum.util.DataIngredient;
import net.minecraft.data.recipes.RecipeCategory;
import net.minecraft.world.item.crafting.CookingBookCategory;

public final class ModExtraRecipes {
    public static void register() {
        MyMod.REGISTRUM.addDataGenerator(ProviderType.RECIPE, prov -> {
            DataIngredient rubyOre = DataIngredient.items(ModBlocks.RUBY_ORE);
            DataIngredient pinecone = DataIngredient.items(ModItems.PINECONE);

            // 1. Generate both smelting and blasting recipes in one call (auto-named <result>_from_<source>_smelting / _blasting)
            prov.smeltingAndBlasting(
                rubyOre,
                RecipeCategory.MISC,
                CookingBookCategory.MISC,
                ModItems.PINECONE,
                0.7f
            );

            // 2. Generate 9-to-1 storage block and 1-to-9 unpacking recipes in one call
            prov.storage(ModItems.PINECONE, RecipeCategory.BUILDING_BLOCKS, ModBlocks.RUBY_ORE);
        });
    }
}
```

## 3. Core Provider & Generator API Reference

### 1. `DataGenContext<R, E>` & `DataProviderInitializer`

| Class | Method Signatures | Description |
| :--- | :--- | :--- |
| `DataGenContext<R, E>` | • `public E getEntry()` / `public E get()`<br>• `public String getName()`<br>• `public Identifier getId()`<br>• `public static <R, E extends R> DataGenContext<R, E> from(Builder<R, E, ?, ?> builder)` | Context object passed to builder datagen callbacks, holding the entry instance, registry name, and `Identifier`. |
| `DataProviderInitializer` | • `public <T> void add(ResourceKey<Registry<T>> registry, RegistrySetBuilder.RegistryBootstrap<T> provider)`<br>• `public void addDependency(ProviderType<?> dependent, ProviderType<? extends RegistrumLookupFillerProvider> parent)` | Manages the datapack `RegistrySetBuilder` and `HolderLookup.Provider` dependencies between `ProviderType`s (each `dependent` allows at most 1 upstream `parent`; throws `IllegalStateException` on cycles). |

### 2. `RegistrumBlockModelGenerator` & `RegistrumItemModelGenerator`

Respectively extend vanilla `net.minecraft.client.data.models.BlockModelGenerators` and `ItemModelGenerators` (exposing previously `protected`/package-private methods and `blockStateOutput`, `itemModelOutput`, `modelOutput` for callbacks):

| Class | Extension Method Signatures | Description |
| :--- | :--- | :--- |
| `RegistrumBlockModelGenerator` | • `public void create(Block block, Identifier model)`<br>• `public void create(Block block, TexturedModel.Provider texture)`<br>• `public Identifier mcLoc(String id)` / `public Identifier modLoc(String id)`<br>• `withBuilder(...)` / `getBuilder()` / `withParent(ModelTemplate / TexturedModel, ...)` → returns `RegistrumLegacyBlockModelBuilder` | Blockstate and block model generator. |
| `RegistrumItemModelGenerator` | • `public void createWithExistingModel(Item item, Identifier id)`<br>• `public void generateTintedModel(Item entry, Identifier model, ItemTintSource tint)`<br>• `public Identifier mcLoc(String id)` / `public Identifier modLoc(String id)`<br>• `public String modid(NonNullSupplier<? extends ItemLike> item)` / `public String name(NonNullSupplier<? extends ItemLike> item)` | Client item model generator. |

### 3. `RegistrumRecipeProvider` & `DataIngredient`

| Class | Key Method Signatures | Description |
| :--- | :--- | :--- |
| `DataIngredient` | • `public static <T extends ItemLike> DataIngredient items(NonNullSupplier<? extends T> first, NonNullSupplier<? extends T>... others)`<br>• `public static <T extends ItemLike> DataIngredient items(T first, T... others)`<br>• `public static DataIngredient tag(TagKey<Item> tag)`<br>• `public static DataIngredient ingredient(Ingredient parent, ItemLike / TagKey<Item> / Identifier, ...)`<br>• `public Ingredient toVanilla()` / `public Identifier getId()` / `public Criterion<...> getCriterion(RegistrumRecipeProvider prov)` | DataGen-specific ingredient wrapper that remembers both the primary `Identifier` (for recipe file naming) and the auto-generated inventory-changed unlock `Criterion`. |

### 4. `RegistrumLootTableProvider`, `RegistrumLangProvider` & `RegistrumGenericProvider`

| Class | Key Method Signatures | Description |
| :--- | :--- | :--- |
| `RegistrumLootTableProvider` | • `LootType.BLOCK` / `LootType.ENTITY` / `LootType.register(name, set, factory)`<br>• `public <T extends RegistrumLootTables> void addLootAction(LootType<T> type, NonNullConsumer<T> action)`<br>• `public void addLootAction(ContextKeySet set, Consumer<BiConsumer<ResourceKey<LootTable>, LootTable.Builder>> action)` | Loot table generator. `RegistrumBlockLootTables` exposes all vanilla `BlockLootSubProvider` methods (`create*Drops`, `dropSelf`, `dropOther`, `dropWhenSilkTouch`, `add`, etc.). |
| `RegistrumLangProvider` | • `public static String toEnglishName(String internalName)`<br>• `addBlock(block)` / `addBlockWithTooltip(block, [name,] tooltip)`<br>• `addItem(item)` / `addItemWithTooltip(item, name, List<String> tooltip)`<br>• `addTooltip(item, String / List<String>)` (auto-generates `<descId>.desc` or `<descId>.desc.0`, `1`, ...)<br>• `add(CreativeModeTab, String name)` / `addEntityType(entity)` | Language file generator outputting both `en_us` and auto-flipped `en_ud`. |
| `RegistrumGenericProvider` | `public RegistrumGenericProvider add(Generator generator)` (where `Generator` is `DataProvider generate(GeneratorData data)`) | Allows mounting any standard Minecraft / NeoForge `DataProvider` inside `ProviderType.GENERIC_SERVER` or `ProviderType.GENERIC_CLIENT` callbacks. |
| `RegistrumProvider` / `RegistrumProviderDelegate` | • `RegistrumProvider#getSide()` (returns `LogicalSide`)<br>• `RegistrumProviderDelegate#getId()` / `#getEntry()` / `#getName()` | Common top-level interface and entry delegate interface for Registrum data providers (extending `DataProvider`), unifying side identification and entry association. |
| `RegistrumTagsProvider<T>` & `IntrinsicAppender<T>` | • `Key#tag(TagKey<T>)` → returns `TagAppender<T>`<br>• `Intrinsic#tag(TagKey<T>)` → returns `IntrinsicAppender<T>`<br>• `record IntrinsicAppender<T>(TagAppender<T> delegate, Function<T, ResourceKey<T>> keyExtractor)`: implements `TagAppender<T>` and adds `add(T)` and `add(T...)` | Tag provider hierarchy. Both `Impl<T>` and `IntrinsicImpl<T>` extend vanilla `TagsProvider<T>`; `IntrinsicImpl<T>` preserves the convenience of passing registry object instances directly via `IntrinsicAppender<T>`. |
